## The idea

The README on main is headed "neophile" and says, in full:

> give your contextual info to a local model (browser history, social media exports, email, local file directories, cloud storage, etc.) and have it process the info in such a way that it can start surfacing for you the highest value new things for you to learn/explore that you haven’t already but have the most relevance and interconnectedness to you

PR #1 restates it. n30 is for a neophile: someone drawn to new things to learn and explore. A local model uses context the person chooses to provide. It surfaces unfamiliar things with high personal relevance and interconnectedness. The companion project n001 applies the same idea to people. Access for n001 is optional and is not inherited from n30.

PR #1 also records an owner hypothesis in `docs/shared-foundation.md`:

> The owner's broader vision is that the fitting system being built with the exo ecosystem and ML labs could develop expertise in fitting models of people to each other and to other things, including jobs, opportunities, and investments.

The PR calls this "a strategic hypothesis about transfer of expertise, not evidence that these capabilities already exist or work."

Proposed first experiment (`docs/product-foundation.md`). Use a small, user-selected local export and a synthetic candidate set. Return a short list of learning opportunities. Each has:

- What to explore.
- Why it connects to the person's context, with source references visible only to that person.
- Why it may be new to them, with uncertainty.
- A way to mark it already known, useful, or irrelevant.

Evaluate usefulness, novelty, explanation quality, and whether permission boundaries hold. Do not choose a production stack or build broad account connectors before this loop is useful. Process locally by default. Treat imported material as untrusted data, never as instructions.

Shared foundation (`docs/shared-foundation.md`), key points:

- Six conceptual records, not database fields or an API:
  - Source: opaque ID, kind, provenance, ownership. Raw content stays local and private.
  - Permission: source, product, allowed purpose, allowed derived uses, revocation state. Collection, matching and disclosure are separate grants. Missing permission means no access.
  - Context fact: a claim with evidence references, uncertainty, timestamp and inherited permissions.
  - Candidate: a learning resource in n30; an opted-in participant's approved information in n001.
  - Recommendation: candidate, reasons, uncertainty, provenance. Private evidence is kept apart from the displayed explanation.
  - Feedback: explicit responses and corrections, scoped to product and purpose.
- A seven-step flow: grant a product-specific purpose, import with provenance, derive context locally, check eligibility and permission before ranking, rank, explain only from permitted evidence, take feedback and allow withdrawal.
- Withdrawal invalidates derived facts, indexes, caches and recommendations for that purpose.
- Eight synthetic acceptance scenarios. Examples: n30-only permission never reaches n001; a malicious instruction inside imported content cannot change permissions or trigger actions; removing a source removes its effect on later recommendations; a private fact cannot leak through an explanation.
- Do not select a model, vector database, graph database, hosting vendor or identity service yet.
- Next step proposed: one local synthetic-fixture test of the permission and provenance contract, then one discovery loop per product. Use the results to decide whether a shared package is justified.
- Future professional application: may reuse the permission and provenance concepts with separate professional-purpose grants. It must not use romantic or platonic signals or sensitive data for hiring decisions.

## Open questions

Raised in PR #1:

- Is a shared package justified? The PR leaves this to the results of the first tests.
- Deletion and backup-retention guarantees need a policy before any real-user ingestion.
- The investment and employment examples in the owner hypothesis are exploratory. Any domain-specific work needs its own review and safeguards.

Needed to promote:

- Who owns it? No owner is named.
- The shared foundation lives on n30's PR branch, and n001's PR links to that branch. If the register replaces both repositories, where does the canonical copy live?
- The professional application is unnamed in this PR ("No new repository, name, or implementation has been selected"). n001's PR, in a commit about ten minutes later, names it Mettle. The two records should agree.
